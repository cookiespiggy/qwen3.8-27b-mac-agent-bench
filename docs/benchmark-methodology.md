# 评测方法论：怎么测才不是「外行跑分」

> 面向所有读者。这篇定义本项目的测试协议：测什么、怎么测、控制哪些变量、
> 结果怎么解读。目的是让结果可复现、可归因——不是「跑得快就是好」。

## 为什么需要方法论

网上很多模型评测是「拉了模型，问几个问题，报个 tok/s 就完事」。问题在于：

1. **tok/s 是污染指标**：思考模式、上下文长度、量化、是否投机解码，都会大幅
   影响 tok/s，不控制变量测出来的数字没法横向对比
2. **没有任务设计**：光聊天测不出「这个模型能不能干活」
3. **不报环境**：硬件、软件版本、参数全不写，别人无法复现

本项目把评测拆成三层，各自回答不同问题。

## 三层评测结构

### 第一层：模型能力基线（Ollama 直连）

回答：「这个模型本身质量如何」——排除 harness 和工具链干扰。

- **指标**：首 token 延迟（TTFT）、解码速度（tok/s）、内存峰值（RSS）
- **方法**：固定 prompt（短/中/长三种长度），固定 `reasoning_effort=low`，
  固定上下文 8K，关闭投机解码，测 3 次取中位数
- **样本任务**：数学（GSM8K 样题）、代码（LeetCode 样题）、中文知识（MMLU-C 样题）
- **产出**：`results/ollama-benchmark.txt`

### 第二层：Agent 能力实测（dsh 驱动）

回答：「模型 + harness + 工具链组合起来，能不能完成真实工程任务」。

- **指标**：任务成功/失败、完成时间、工具调用数、会话 token 消耗、错误次数
- **任务集**：4 个难度递增的 coding agent 任务（见 `benchmarks/README.md`），
  每个都有可执行的测试脚本作为「完成」的客观判据
- **方法**：每个任务在**独立的工作副本**里跑，模型全程无预知；dsh 只能
  读/写工作区内的文件，不能访问外部网络
- **产出**：`results/` 下的 JSONL 会话 + `results/agent-tasks-summary.md`

### 第三层：横向对比

回答：「它跟别的硬件/引擎比处在什么位置」。

- **社区基线**：M5 Pro 64GB（Just Jason）、RTX 4090/3090、M4 系列（oMLX 基准）
- **本机对比**：同一模型，Ollama vs oMLX（如果装得下）
- **注意**：引擎差异（llama.cpp vs MLX vs vLLM）比硬件差异影响更大，横向对比
  只给量级参考，不给结论

## 控制变量清单（每次跑都要记录）

| 变量 | 本项目锁定值 | 为什么 |
|---|---|---|
| 量化 | Q4_K_M | 与 Ollama 官方标签一致 |
| KV cache | q8_0 | 24GB 硬件决策 |
| 上下文 | 8192 | 内存甜点 |
| Flash Attention | 1 | 省内存 |
| 思考模式 | low | 全评测统一 |
| 采样温度 | 0.6（默认） | 可复现 |
| 投机解码 | 关闭 | 排除 draft 干扰（Ollama 对 MTP 支持有限） |
| Ollama 版本 | 0.32.14 | 锁定 |
| dsh 版本 | 0.1.0-rc.7 | 锁定 |
| 网络 | Agent 无外网 | 防止查题作弊 |

## 指标定义（避免歧义）

- **TTFT（Time To First Token）**：请求发出到收到第一个 token 的时间。
  prefill 快慢的直接体现
- **tok/s**：总生成 token 数 ÷ 总生成时间（不含 prefill）。
  注意：含思考 token 的 tok/s 会比纯回答低，要分开报
- **RSS**：模型进程常驻内存。24GB 机器上，RSS 逼近 24GB 就意味着 swap 风险
- **任务成功率**：该任务配套测试脚本全过 = 成功。部分过 = 部分成功

## 结果解读原则

1. **tok/s 不是唯一指标**：一个 30 tok/s 但任务全挂的模型，不如 15 tok/s
   任务全过的模型。Agent 评测里「完成任务」比「生成快」重要
2. **量化质量 vs 速度是 trade-off**：Q4 省内存也更快，但代码任务对精度敏感。
   如果 Agent 任务因「代码语法错误」反复失败，要归因到量化而非模型能力
3. **思考模式要单独报**：`reasoning_effort` 直接影响 token 消耗和 tok/s，
   不标明思考模式的跑分没有意义
4. **一次测 3 次取中位数**：单次结果方差大（内存压力、后台进程、温度采样），
   3 次取中位数是低成本高收益的做法

## 可复现性承诺

- 所有脚本在 `scripts/`，所有任务在 `benchmarks/`，所有原始输出在 `results/`
- 每次运行前 `git status` 确认干净，避免任务文件被污染
- 结果文件命名带时间戳：`results/agent-task1-2026-08-18T1042.jsonl`
- 欢迎任何人按本文档在自己的机器复现，PR 补充更多机型数据

## 诚实声明（本项目不做的）

- 不做「跨引擎同量化」的严格对比（Ollama GGUF vs MLX 的 KV 实现不同，
  严格对比需要各自独立调参，超出 24GB 机器能力范围）
- 不报告官方 benchmarks 卡片的数值（那是 vendor 自测，无独立复现）
- 不把 8K 上下文的结果外推到 262K（内存不允许，且 DeltaNet 长程 recall
  在长上下文的表现本就是未证实的研究问题）
